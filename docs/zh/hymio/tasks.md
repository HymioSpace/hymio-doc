# 任务与多 Agent 工作

任务页只回答一个问题：**接下来还需要做什么，已经产出了什么？**

它不是 cron 编辑器，也不是原始 Agent 调试器。Hymio 展示由 Oath 持有和执行的 Task，保持一级信息
简洁，并把 Agent context、通信和工具调用放到更深一层。

## 用户看到什么

任务工作区默认打开 **任务列表**，不是日历：

- **长期任务**：周期执行或持续追踪，之后仍可能由 Supervisor 唤醒；
- **临时任务**：预期完成后停止；
- 异常出现在对应任务内部。

已完成和已取消任务离开当前列表，保留在 **归档**。归档仍然区分成功结果与取消；从归档移除只
改变展示，不删除 Task 和执行记录。

iOS 可以在任务列表与月、周、日之间切换。日历块来自真实任务 occurrence 和周期投影；没有时间的
任务不会被塞进虚构日期。

页面顶部不再重复显示预算告警。如果某个任务预算耗尽，只在该任务内部展示；原始 token 数字进入
任务详情里的本次运行区域。任务会提示用户直接在对话中让 Agent 继续；主 Agent 可以调用
`task_adjust_budget` 从检查点继续 **同一个 Run**。任务 UI 不提供预算编辑器。

## 一个目标，两个维度

| 维度 | 取值 | 含义 |
| --- | --- | --- |
| 时间 | 临时 / 长期 | 一次性有界结果，还是持续追踪/周期执行 |
| 执行 | 自动执行 / Agent 并行 / Agent Team / 动态工作流 | 当前 Run 如何完成 |

执行方式不会强制绑定定时任务。临时任务可以使用 Agent Team，长期任务也可以使用确定性的 program。

触发可以是一次性、每日 / 每周、显式事件或手动继续。提醒只是程序动作的一种，不是 Task 的定义。

## 用用户语言理解四种执行方式

| 标签 | 什么时候使用 | 一级界面看到什么 |
| --- | --- | --- |
| 自动执行 | 固定动作即可，不需要模型 | 发送中 / 回执 / 已完成 |
| Agent 并行 | 独立工作可拆分后合并 | Leader 和绑定成员 |
| Agent Team | 成员执行中需要沟通 | Leader、成员和 `A → B` 消息 |
| 动态工作流 | 步骤之间存在依赖 | DAG、有向依赖边和节点结果 |

执行方式只显示短标签。旁边的小问号按需提供解释，不在页面正文里堆说明。

## Task、Run 与 Agent

| 记录 | 含义 |
| --- | --- |
| Task | 持久目标与策略 |
| Run | 一次执行尝试 |
| TaskAgent | 对该 Run 负责的 Agent |
| Subagent | 绑定到同一 Run 的 Team 成员或工作流节点 |

每个 Subagent 都必须属于一个 TaskRun。这样才能回答“谁在为哪项任务工作”，取消时也能准确停止相关执行。

一个 Task 只负责一个连贯结果。每个被委派的 Subagent 或 Workflow 节点都必须明确交付物、输入来源、
负责范围、排除项/非目标、可观察验收标准和遇到阻塞时的停止条件。最终整合与完成仍由 TaskAgent 负责。

## 状态语言

### Task

- active；
- paused；
- closed：achieved、cancelled 或 expired。

### 当前 Run

- 准备中；
- 进行中；
- 等待明确条件；
- 因需要处理而暂停；
- 已完成；
- 未完成；
- 已取消。

“等待”本身不是异常。普通通知正在发送也可以处于等待态。只有需要用户决定，或执行 blocked/failed，
才应显示成需要关注。

### Supervisor

Supervisor 检查持久化的触发时间、等待、租约、超时、预算和消息，在条件满足时请求唤醒。它不独立
理解用户目标，也不声称任务在语义上已经正确。绑定到 Run 的 TaskAgent 负责执行、证据和完成报告。

## 查看任务详情

一级详情保持：

1. 标题和当前状态；
2. 一个时间标签和一个执行方式标签；
3. 遇到异常时显示原因；
4. 当前 Run 进展和紧凑预算；
5. 计划或工作流依赖；
6. Leader 与绑定成员；
7. 用户可见的最终结果。

任务定义默认折叠。事件 payload 和原始工具 JSON 不进入 C 端任务页。

## Agent 协作

并行 Subagent 任务在一级界面展示 TaskAgent 和绑定成员。Agent Team 的通信必须写清方向：

```text
架构模式调研 → 调研 Leader
调研 Leader → 框架选型
```

发送者和接收者都必须有名字。打开成员后可以查看：

- 职责与验收；
- Team 通信；
- 按时间排序的执行记录；
- 有语义描述的工具调用。

工具调用默认折叠。Agent 提供 description 时，不使用“执行命令”“browser”之类实现名代替用户可理解的意图。

现在每次 Oath 工具调用都必须提交简短 `description`。探索过程优先显示这句话，工具名作为次要
上下文；原始参数和 result JSON 留在 Agent 或 Trace 详情。

## 动态工作流

动态工作流在任务页以真正的 DAG 展示。有向边表示真实依赖；同一层没有依赖关系的节点可以并行：

- 等待依赖；
- 正在执行；
- 执行已暂停；
- 已完成；
- 失败或阻塞。

“等待依赖”只对应 `pending`，表示启动条件尚未满足。已经开始的节点因预算或任务暂停而停下时，
状态必须是 `paused`，不能退回 `pending`；恢复后继续同一个节点和 Agent。取消 Task 时，所有尚未
成功的节点都进入 `cancelled`，不能继续显示“等待依赖”。

选择节点后可以查看输入、结果、错误和绑定 Agent activity。动态工作流不展示 Agent 间通信，因为
通信属于 Agent Team，而不是依赖图。

初始任务计划由创建 Task 的交互 Agent 提出；运行中的 DAG 属于绑定的 TaskAgent，只有它调用
`workflow_define`，交互 Agent 不能替这个 Run 定义节点。第一次定义到达前，任务页显示
**工作流准备中**，而不是一段空白。DAG 节点持久化在 Oath 的 `task_workflow_nodes` SQL 表中，
JSON 依赖字段是关系状态的一部分，不是独立 DAG 文件。

所有依赖节点成功以后，Leader 才会被唤醒整合。上游失败会让下游进入 blocked，而不是在没有输入时继续执行。

## 取消、暂停与移除

### 取消

取消是终态：

- Task 和打开的 Run 都变为 cancelled；
- 未来 trigger 停止；
- 绑定成员停止或被取消；
- 卡片立即从当前任务消失；
- 进入归档并标记为“已取消”，不会计入“已完成”。

对话仍然保留。取消影响该任务，不影响账号或聊天记录。

### 暂停

暂停保留 Run 和检查点，供之后恢复。如果暂停原因是预算或进展限制，对应任务会解释该原因。
遇到 `BUDGET_EXHAUSTED` 时，用户在对话中确认继续，主 Agent 再提高当前 Run 预算。

### 从当前视图移除

已完成或已取消任务从归档移除只表示视图变化。后端保存按所有者隔离的隐藏标记，不删除历史，
也不表示任务成功或已经撤销外部副作用。

## 通知

这里有两个不同概念：

1. **通知策略**决定 Hymio 可以使用哪些渠道，以及在什么条件下发送。
2. **Agent notify 请求**是 Agent 提出展示更新的语义请求，不会覆盖用户设置、前台抑制、去重或审批规则。

任务完成与通知送达也彼此独立。结果可以已经完成，而通知仍在等待或发送失败。

## 为什么任务归 Oath

Hymio 不再维护第二套调度器和任务数据库。

- Oath 持久保存 Task、Run、检查点、预算和 Agent 执行；
- Hymio 负责鉴权，把 Oath 结果投影成产品 API，并负责界面；
- 暂停、恢复和取消转发给 Oath；
- Oath 请求结果投递后，Hymio 再通过配置渠道发送通知。

这样可以避免“任务页显示 running，但执行端已经 paused”的双状态冲突。

## API

Hymio 提供：

- `GET /tasks`；
- `POST /tasks`，action 为 `get`、`pause`、`resume`、`cancel`、`archive_list` 或 `archive_hide`。

Task 创建和要求修改仍由 Agent 管理。普通 HTTP 客户端不能伪造内部 pending 状态，也不能绕过 Oath
校验。`task_adjust_budget` 只暴露给 Agent，不是公开 HTTP action，也不增加任务配置 GUI。

## 设计原则

- 展示工作，不展示实现；
- 异常放在对应任务内部；
- 永远不把取消算作完成；
- 不在页头和任务卡重复同一条告警；
- 使用短标签和渐进披露；
- Agent 通信必须带方向；
- 原始工具和 trace 下沉一层；
- 完整覆盖 loading、empty、error 和 cancelled。
