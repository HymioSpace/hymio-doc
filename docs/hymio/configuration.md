# Configuration & deployment

Start with the unified local installation. Edit the operator input file; service configuration generated from it is rewritten on startup.

## Real case: connect phone and computer to one deployment

The native iOS build and Web both used the running development backend. Under the same demonstration account, Web read the `MiniMax-M3` preference saved on iPhone and restored the phone's packing-list conversation.

A useful configuration acceptance check is the same account, backend, model preference and conversation content, not merely two accessible interfaces. Do not copy local caches to compensate for mismatched deployments or accounts. See the [model case captures](./media).

## Local configuration

`hymio init` creates `~/.hymio/config.toml` with private permissions. A minimal optional desktop configuration looks like this; add it to the file generated by init rather than replacing all existing fields:

```toml
computer_provider = "daytona"
daytona_api_key = "" # Or provide DAYTONA_API_KEY at startup
admin_user_ids = [] # Product user IDs, not names
lan_host = "off"   # Use "auto" for LAN development
```

| Setting | Use |
| --- | --- |
| `minimax_api_key`, `minimax_api_base` | Model account and compatible endpoint |
| `models`, `vision_model` | Conversation allowlist and media model |
| `daytona_api_key`, `daytona_api_url`, `daytona_snapshot` | Hosted desktop connection |
| `admin_user_ids` | Operator-console access |
| `device_api_targets` | Operator-assigned HTTPS device hosts |
| `casdoor_port` | Identity service port; default 8000 |
| `invitation_codes` | Local signup invitation list |
| `lan_host` | `off`, `auto`, or configured LAN host |

The [complete input template](https://github.com/HymioSpace/Hymio/blob/main/deploy/config.example.toml) describes defaults. `MINIMAX_API_KEY`, `DAYTONA_API_KEY` and `E2B_API_KEY` can supply credentials; keep literal keys out of commands and source control.

## Start, inspect, restart

```sh
hymio start --client web --timeout 900
hymio status
hymio logs -f
hymio restart
hymio doctor
```

Use `hymio doctor` to identify active configuration mode. Unified output lives under `~/.hymio/local-<id>/`. Do not hand-edit generated Backend or Oath files there.

## Another computer

Copy the private input file for an independent fresh installation, set permissions to `600`, and install prerequisites on the new machine. Accounts, history, tasks and device bindings are database state, not configuration. Migrating them requires a consistent backup and restore.

## LAN and iOS

Set `lan_host = "auto"` in unified local input and restart. Clients use the resulting public Backend entry rather than manually rewriting Oath, auth and media addresses. See [Cross-device continuity](./ios) for feature use and the captured two-client workflow.

## Public cloud

Cloud deployment combines HTTPS routing, Web, Backend, identity and Oath. Product settings, independent Oath configuration and deployment routing have different responsibilities:

```text
/opt/hymio/config/hymio.toml    product / service settings
/opt/hymio/config/oath.toml     independent runtime settings
/opt/hymio/config/cloud.toml    deployment / domains
/opt/hymio/config/private/      credentials
```

Keep HTTPS/WSS, allowed origins and OIDC callbacks consistent with the chosen public origin. Preserve databases, Vault recovery material and identity data in backups.


The cloud source directory is `deploy/cloud`. Prepare a domain and HTTPS, install Docker, Compose, Python 3.11+ and Oath, and configure Backend, Oath, identity and private credentials on the host. The current topology supports one host and one Backend instance.

Once Oath is running and its network name matches `cloud.toml`, run from the Hymio repository:

```sh
python3 deploy/cloud/manage.py prepare --config /opt/hymio/config/cloud.toml
python3 deploy/cloud/manage.py start --config /opt/hymio/config/cloud.toml
```

Container startup still requires identity-service organization, login application and callback configuration. Health checks do not prove the model can reply: sign in, send a short message, then verify task and device authorization paths.

## Troubleshooting

Start with `hymio status`, `hymio doctor` and `hymio logs -f`, then locate the failing boundary:

| Symptom | First check |
| --- | --- |
| Page loads but sign-in fails | Identity configuration, callback and Backend reachability. |
| Connected without an agent reply | Oath Worker logs, Skill readability and model errors. |
| Provider rejects authentication or quota | Model allowlist, provider credentials and balance. Do not loop over rejected paid requests. |
| Tool hangs | Oath Tools, Backend device records, timeout and device lock. |
| Device stays preparing | Existing allocation and recovery records. A timeout does not prove nothing was created. |

Application containers use UID `10001`. Directories must be traversable and Skill files readable. Private configuration needs restricted permissions and ownership readable by its runtime identity; do not loosen the entire tree recursively. Remove credentials before sharing errors and diagnostic records.
